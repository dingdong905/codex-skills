# 文档类型与结构合同

只读取当前任务对应的文体部分，再打开该部分指向的模板。文体由读者要完成的任务决定，不由用户随手写的文件名决定。

## 快速路由

| 读者当前要做什么 | 选择 | 模板 |
| --- | --- | --- |
| 按步骤完成操作或排障 | SOP / Runbook | [sop-runbook.md](../assets/templates/sop-runbook.md) |
| 安装、部署或配置一个系统 | 部署与操作指南 | [deployment-guide.md](../assets/templates/deployment-guide.md) |
| 还原故障并推动改进 | 故障记录 / 事故复盘 | [incident-postmortem.md](../assets/templates/incident-postmortem.md) |
| 评审并安全执行一次变更 | 变更工单 | [change-plan.md](../assets/templates/change-plan.md) |
| 用统一标准判断交付是否合格 | 验收标准 | [acceptance-standard.md](../assets/templates/acceptance-standard.md) |
| 比较选项、确定设计或验证可行性 | 方案 / RFC / POC | [proposal-rfc-poc.md](../assets/templates/proposal-rfc-poc.md) |

边界判断：

- 用户要“照着做”用 SOP 或部署指南；要“理解为什么”不属于本批模板，应写技术说明。
- 部署指南围绕一个交付目标，SOP 围绕一个可重复操作或故障分支。两者可以互相链接，不合并成大全。
- 故障记录只需还原事实；要解释系统性原因并追踪改进时，使用完整复盘结构。
- 变更工单服务于一次受控执行；方案/RFC 服务于执行前的选择，不能互相替代。
- 验收标准定义规则；某次项目的验收结果应单独记录证据和结论。

## SOP / Runbook

适用于重复操作、值班处置、故障定位、扩缩容、证书更新等需要按步骤执行的任务。

必须回答：

- 谁在什么条件下可以执行；
- 需要哪些输入、权限和工具；
- 每一步做什么、为什么做、看到什么算正常；
- 不符合预期时走哪条分支；
- 哪些情况必须停止、回滚或升级；
- 升级时要提供哪些证据。

写法要求：

- 一步只包含一个主要动作，命令与预期输出紧邻出现。
- 判断节点使用明确条件，不写“视情况处理”“确认正常”。
- 危险命令说明影响范围和恢复条件；不可逆操作不得作为默认路径。
- 长命令参考、现象对照和术语放附录，主流程保持连续。

不要写成原理文章或个人排障日记。原理说明链接出去；历史过程进入故障记录。

使用模板：[sop-runbook.md](../assets/templates/sop-runbook.md)

## 部署与操作指南

适用于安装、部署、升级、接入或配置一个明确系统。它面向已经具备必要基础知识、希望完成目标的读者。

必须回答：

- 支持哪些版本、环境和架构；
- 开始前必须具备什么；
- 哪些变量需要按环境替换；
- 每个阶段如何验证，而不是只给命令；
- 如何回滚、卸载或恢复到部署前状态；
- 常见失败如何定位。

写法要求：

- 先给最终状态和适用范围，再给准备工作。
- 命令应可复制，但密钥、真实账号、生产地址等敏感值使用明确变量。
- 区分命令、配置文件和预期输出，分别使用代码块。
- 多环境差异集中写入版本/环境矩阵，不在每一步反复插入条件。

不要把参考参数、概念解释和教程练习全部塞入主线。参数表和原理说明应链接到独立文档。

使用模板：[deployment-guide.md](../assets/templates/deployment-guide.md)

## 故障记录 / 事故复盘

适用于线上故障、重大异常、重复问题或需要跨团队吸取经验的事件。

必须回答：

- 发生了什么，影响了谁、多久和多大范围；
- 如何发现、响应和恢复；
- 哪些证据排除了什么假设；
- 直接根因和促成因素分别是什么；
- 修复如何验证；
- 哪些改进能降低再次发生的概率或影响。

写法要求：

- 摘要先给影响、根因和当前状态，排查细节放后面。
- 时间线只写关键状态变化、决策和证据，不复制聊天记录。
- 根因描述系统、流程或防护缺口，不把个人当作根因。
- 行动项必须可关闭，写负责人、期限和状态；“加强监控”“提高意识”不是合格行动项。
- 区分临时恢复、永久修复和预防措施。

短故障记录可以省略复盘性的章节，但不能省略影响、证据、修复和验证。

使用模板：[incident-postmortem.md](../assets/templates/incident-postmortem.md)

## 变更工单

适用于生产或共享环境中的上线、配置调整、扩缩容、数据迁移和组件替换。

必须回答：

- 为什么现在要变，具体改哪些对象；
- 变更窗口、影响、风险级别和操作角色；
- 开始前哪些条件必须满足；
- 每一步的操作、预期结果和执行人；
- 哪些指标证明成功，观察多久；
- 出现什么信号立即回滚，如何回滚并验证恢复。

写法要求：

- 风险等级与实际影响匹配，不能只粘贴等级定义。
- 回滚触发条件必须可观察，例如错误率、不可用时长或检查失败。
- 回滚步骤与正向步骤同样具体，事先确认备份、旧版本和权限可用。
- 把审批、操作、复核和观察角色分开；未知人员标记待确认。

不要只写“流水线回滚即可”或“观察正常后结束”，需要说明入口、目标版本和判定标准。

使用模板：[change-plan.md](../assets/templates/change-plan.md)

## 验收标准

适用于交付转维、平台上线、项目验收、基线检查和合规检查。

必须回答：

- 标准适用于什么对象和阶段；
- 每项要求是必须、建议还是不适用；
- 使用什么方法验证，留下什么证据；
- 达到什么阈值算通过；
- 例外如何申请、批准和到期复查。

写法要求：

- 每项使用稳定编号，便于引用、评论和历史追踪。
- 一项只检查一个可判定条件；避免把多个要求塞进同一单元格。
- “已部署”“已接入”不等于验收要求，需补可观察结果或阈值。
- 标准正文与实际结果分离；实际验收记录写状态、证据、验证人和日期。

分类应跟随系统质量属性或交付阶段，不能只按编写人所在团队划分。

使用模板：[acceptance-standard.md](../assets/templates/acceptance-standard.md)

## 方案 / RFC / POC

适用于需要评审方向、比较选项、记录设计或通过实验验证关键假设的工作。

必须回答：

- 要解决的具体问题和不解决的内容；
- 当前约束、关键假设和成功标准；
- 考虑过哪些选项，各自代价是什么；
- 最终建议及其理由；
- 如何验证、上线、观测和回退；
- 仍有哪些未决问题。

写法要求：

- 开头直接给建议和需要评审者决定的事项。
- 方案比较使用同一组维度，写出负面和中性后果。
- POC 必须先写待验证假设、指标和通过阈值，再写实验结果。
- 架构图必须配文字说明关键数据流、边界和故障路径。
- 已批准的重要架构决策可在文末提炼为 ADR：Status、Context、Decision、Consequences。

不要用大量背景掩盖没有选择，也不要把实现步骤冒充方案比较。

使用模板：[proposal-rfc-poc.md](../assets/templates/proposal-rfc-poc.md)
